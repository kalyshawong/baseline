## Medium

### BUG-M1 — `/api/sync` same-origin auth is spoofable and over-broad
**File:** `src/app/api/sync/route.ts:24-41`

```ts
let isFromApp = secFetchSite === "same-origin" || secFetchSite === "same-site";
if (!isFromApp && referer) {
  const refHost = new URL(referer).host;
  isFromApp =
    (!!host && refHost === host) ||
    (appUrl ? referer.includes(appUrl) : false) ||
    refHost.endsWith(".vercel.app") ||
    referer.includes("localhost") ||
    referer.includes("127.0.0.1");
}
if (!isFromApp && authHeader !== `Bearer ${apiKey}`) {
  return NextResponse.json({ error: "Unauthorized" }, { status: 401 });
}
```

The new logic tries to let the in-app Sync button fire without a key while still
requiring `SYNC_API_KEY` for cron. The problem is every signal it trusts is
attacker-controlled from a non-browser client:

1. **`Sec-Fetch-Site` is only unspoofable from inside a real browser.** It's a
   forbidden header *for `fetch()`*, but `curl`/any server can send
   `Sec-Fetch-Site: same-origin` freely. So the first check reduces to "send one
   header and skip auth entirely."
2. **`refHost.endsWith(".vercel.app")`** trusts *every* `*.vercel.app` deployment,
   not just this app's. Any Vercel-hosted page can set a matching referer.
3. **`referer.includes(appUrl)` / `.includes("localhost")`** are substring matches.
   With `appUrl = "https://baseline.app"`, a referer of
   `https://baseline.app.evil.example` passes; so does anything containing the
   literal `localhost`.

`/api/sync` triggers `syncOuraData()` — external Oura API calls plus heavy batched
DB writes — with no rate limit. So the illusory boundary is a cost/DoS lever, not a
data-injection one (the endpoint pulls, it doesn't accept arbitrary rows).

**Why MEDIUM, not HIGH:** today `/api/sync` is *not* exempt from the
`SITE_PASSWORD` middleware gate (`middleware.ts:14-20` only exempts `_next`,
`/api/healthkit-sync`, and static extensions), so in the gated prod deploy a raw
external POST is blocked by Basic Auth before it reaches this handler. It's also
single-tenant (`getCurrentUserId()` = `SOLO_USER_ID` shim). The risk is latent: the
comments make clear this same-origin check is *intended* to become the real auth
boundary in Phase 2, and when the interim Basic-Auth gate is removed, a spoofable
header is not an acceptable boundary — especially multi-tenant, where triggering a
sync must be scoped to the authenticated user.

**Fix:** Don't treat `Sec-Fetch-Site`/referer as authentication. For the on-demand
button, gate on the real per-user session once Phase-2 auth lands (the sync then runs
for `session.userId`). Until then, keep the `SYNC_API_KEY` bearer check as the only
trusted path and let the middleware Basic-Auth gate cover the browser button. If a
same-origin fast-path is kept as defense-in-depth, drop the `.vercel.app` blanket and
replace the `includes()` referer checks with exact host equality
(`refHost === host`). Carry this into the same Phase-2 auth work as BUG-L1 from the
last scan.

## Low

### BUG-L1 — `mobile-quick-tag.tsx` silently drops a failed tag POST (BUG-009 regression)
**File:** `src/components/mobile/mobile-quick-tag.tsx:43-67`

```ts
const res = await fetch("/api/tags", { method: "POST", ... });
if (res.ok) {
  setFlash(tag); ... router.refresh();
}
// no else — a failed POST does nothing at all
```

The desktop BUG-009 fix established the convention that every client fetch checks
`res.ok` **and shows an inline error on failure**. This new mobile component checks
`res.ok` but has no `else`: if the tag save fails, the user gets no flash and no
error — the tap looks like a no-op. Low impact (no data corruption, no stale
optimistic state since `flash` only sets on success, and the user can retry), but it
reintroduces exactly the silent-failure pattern the team already decided to fix.
The sibling mobile components (`mobile-log-food`, `mobile-goals`, `mobile-cycle-card`)
all handle the failure branch — this one is the outlier.

**Fix:** Add an `else` that surfaces a brief inline error (mirror
`mobile-log-food.tsx`'s error state), or a catch around the fetch.

### BUG-L2 — `processWorkouts` builds bulk HR insert via `$executeRawUnsafe` string interpolation
**File:** `src/app/api/healthkit-sync/route.ts:390-402`

```ts
const values = batch
  .map((p) => `('${userId}', ${p.bpm}, '${p.source}', '${p.timestamp.toISOString()}')`)
  .join(",\n");
await prisma.$executeRawUnsafe(`INSERT INTO "HeartRateSample" ... VALUES ${values} ...`);
```

Currently **safe**: `userId` is internal (`getCurrentUserId()`), `bpm` is
`Math.round(...)` and `Number.isFinite`-guarded, `source` is a hardcoded literal
(`"apple-watch-workout"`), and `timestamp` is a `Date.toISOString()` (throws
`RangeError` on an invalid date, caught by the surrounding try). No field is a raw
attacker string, so there's no live injection. Logged as LOW because it's a fragile
pattern — if `source` or any interpolated field ever becomes payload-derived, this
becomes a SQL-injection sink. The comment notes SQLite's adapter forced the raw
path; on the current Postgres backend, `createMany({ skipDuplicates: true })` or a
`Prisma.sql` parameterized template would remove the sharp edge.

**not** re-flagged as standalone bugs — they belong to the scoped-query-layer
migration. New sites this window added to that backlog:

  (`heartRateSample.aggregate`) filters only on `source: { startsWith: "apple" }` and
  the workout time window, **no `userId`**. Cross-user read: another tenant's Apple HR
  samples in the same wall-clock window would fold into this workout's avg/max/min.

  on `where: { id }` (the Oura record id) with no `userId` in the conflict target.
  Oura ids are globally unique so collision risk is low, but the write isn't
  tenant-scoped and the sibling daily upserts all use `userId_day`.

All latent today (single-tenant `SOLO_USER_ID` shim); logged so the diff-window
additions are visible to the migration effort, not for ad-hoc fixing.
