## High

### BUG-H1 — `/api/workout-notes/[id]/analyze` has no rate limiting on the Anthropic call
**File:** `src/app/api/workout-notes/[id]/analyze/route.ts:174-183`

```ts
const response = await withAnthropicRetry(
  () => client.messages.create({
    model: "claude-sonnet-4-6",
    max_tokens: 600,
    system: ANALYZE_SYSTEM_PROMPT,   // ~1.5k-token system prompt
    messages: [{ role: "user", content: userMessage }],
  }),
  { label: "workout-note-analyze" },
);
```

This is a new user-triggered AI endpoint (the "analyze" button on the workout card)
that fires a Sonnet request on every POST with **no throttle**. `withAnthropicRetry`
handles *transient server errors* but is not a rate limiter — it has no per-key budget,
and on a 429 it will actually *retry up to 4×*, amplifying cost under load. The
`/api/coach` route added exactly this guard in the BUG-004 fix (`checkRateLimit("coach")`,
`route.ts:19,83`); this endpoint was authored without reaching for it.

This is the BUG-004 family. The codebase's own convention rated "no rate limiting on
the Claude API" as **CRITICAL** for coach. Blast radius is smaller here — each call is
single-shot with a hard `max_tokens: 600` (not a growing chat context), and the
`SITE_PASSWORD` gate keeps it off the open internet for now — so it's logged as **HIGH**
rather than Critical. But this matters specifically because Baseline is heading to a
public multi-tenant deploy this summer: an authenticated-but-unthrottled AI endpoint
that costs money per click is an abuse/cost vector that should not ship to other users.

A secondary, lower-risk instance of the same gap: `classifyGiFields` →
`classifyNarrative` (`gi-classifier.ts:119`) also calls Sonnet with no rate limit on
every WorkoutNote **save**. It's materially safer (gated behind a keyword pre-filter
that emits "none" with zero API calls for most narratives, and tied to a save action
rather than a spammable button), so treat it as part of this fix, not a separate bug.

**Fix:** Extract the in-memory limiter from `coach/route.ts` into
`src/lib/rate-limit.ts` (a shared `checkRateLimit(key, { max, windowMs })`) and call it
at the top of the analyze handler (e.g. 10 analyses/min) and inside `classifyNarrative`
before the LLM stage. When the public auth layer lands (Phase 2), re-key the limiter on
`userId` instead of a global string. Keep the per-call `max_tokens` cap as the
second line of defense.

## Medium

### BUG-M1 — `captureSignalsForDate` runs an unguarded `Promise.all`; one failed daily-table read fails the whole note save
**File:** `src/lib/workout-notes.ts:187-205` (called from `workout-notes/route.ts:109`)

```ts
const [sleep, readiness, stress, phase, periodDay, recentSleep] =
  await Promise.all([
    prisma.dailySleep.findUnique(...),
    prisma.dailyReadiness.findUnique(...),
    prisma.dailyStress.findUnique(...),
    resolveCyclePhase(utcDay),
    getCurrentPeriodDay(utcDay),
    prisma.dailySleep.findMany(...),
  ]);
```

The signal snapshot is explicitly *best-effort* context — the surrounding code already
null-coalesces every field, and the doc comment says "missing data is fine; we just
record null." But `Promise.all` rejects if **any** of the six promises throws (a DB
timeout, a transient connection error, a bug in `resolveCyclePhase`). Because this runs
*inline* in the POST handler before `prisma.workoutNote.create`, a single failed
auxiliary read throws past the snapshot and out to the route's catch → **500, and the
user's narrative is never saved.** That inverts the intended failure mode: the note
(the thing the user actually typed) should always save; the snapshot should degrade to
nulls. This is the BUG-006 family (`Promise.all` → `Promise.allSettled`), the same fix
already applied to `buildCoachContext`.

**Fix:** Swap to `Promise.allSettled` and extract each value with a fallback (mirror
the `val()` extractor pattern from `coach-context.ts`), or wrap the whole snapshot in a
try/catch that returns an all-null `SignalSnapshot` on failure. Either way, note
creation must not depend on the snapshot succeeding.

### BUG-M2 — `getHyroxToday` signal fan-out is also an unguarded `Promise.all`
**File:** `src/lib/hyrox-today.ts:67-90`

Same shape as BUG-M1: a 5-way `Promise.all` over readiness/sleep/cv-signals/cycle/last-
session feeds the dashboard `HyroxCountdownCard` (a server component) and
`/api/hyrox/today`. If any leg throws, the entire card crashes rather than rendering
with partial context (e.g. readiness present, cycle phase missing). Lower severity than
BUG-M1 because it's a read path with no data-loss consequence — worst case the card
fails to render — and the `/api/hyrox/today` caller has an outer try/catch. Still worth
converting to `allSettled` so a single missing daily row doesn't blank the card.

**Fix:** `Promise.allSettled` + per-leg fallback, identical pattern to BUG-M1.

## Low

### BUG-L1 — `SITE_PASSWORD` gate: non-constant-time compare + over-broad static exemption
**File:** `src/middleware.ts:18,33`

Two minor issues in the interim access gate:
1. `if (pass === pw)` (line 33) is a plain string comparison — not constant-time, so it
   is theoretically timing-attackable. For a shared site password behind a single env
   var this is low-stakes, but `crypto.timingSafeEqual` is a one-liner.
2. The static-asset exemption regex (line 18) exempts **any** path ending in
   `.js`, `.json`, `.txt`, etc.: `/\.(?:png|svg|ico|webmanifest|js|txt|woff2?|json)$/`.
   No current route ends in those extensions, so there's no live bypass, but a future
   route like `/api/export.json` would silently fall outside the gate. Tighten to the
   specific PWA asset paths, or scope the exemption to `/_next` + an explicit allow-list.

This whole gate is slated for replacement by real auth in Phase 2, so neither is urgent
— logging so the constant-time compare gets carried into the real auth implementation.

## Cross-cutting note — new unscoped-query sites added this window

`MULTITENANCY_AUDIT.md` already owns the missing-`userId` problem and prescribes a
centralized scoped-query layer, so this is **not** re-flagged as individual bugs. But
for the migration backlog, the code authored *this window* added new unscoped reads that
violate the `current-user.ts` invariant ("every query/write should scope to
`getCurrentUserId()`") — writes correctly use `userId`, but several companion reads do
not:

- `hyrox/sessions/route.ts:84` — `hyroxPlan.findFirst({ where: { status: "active" } })`
  (the create on line 111 *does* set `userId`, but it attaches to whatever user's active
  plan `findFirst` returns).
- `hyrox-today.ts:58` and `hyrox/today/route.ts:35` — same unscoped active-plan lookup.
- `workout-notes.ts:200` — the HRV-CV `dailySleep.findMany` window has no `userId`
  (the sibling `findUnique`s on lines 189-191 *do* use `userId_day`; the inconsistency
  is the tell).
- `workout-notes/[id]/analyze/route.ts:86` and `workout-notes/[id]/route.ts:47` —
  `workoutNote.findUnique({ where: { id } })` by id only.
- `workout-notes.ts:85,98` — `getWorkoutByIdAndSource` looks up HK/Oura workouts by `id`
  with no `userId`.

Recommendation: don't fix these ad hoc — fold them into the scoped-query-layer migration
so they're covered by the same backstop as the existing 305 sites. Logged here only so
the diff-window additions are visible to that effort. (All are latent, not live: today
`getCurrentUserId()` is the hardcoded `SOLO_USER_ID` shim, so there is one tenant and no
cross-user read is currently possible.)
