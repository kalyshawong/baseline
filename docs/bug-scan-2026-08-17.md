## Critical

### BUG-C1 — HealthKit ingestion key shipped to the browser as `NEXT_PUBLIC_`, guarding a gate-exempt write endpoint
**Files:** `src/components/native/native-health-init.tsx:35`, `src/middleware.ts:15-18,47`,
`docs/capacitor-healthkit-setup.md` ("Key note" section)

```ts
const key = process.env.NEXT_PUBLIC_HEALTHKIT_SYNC_KEY;
...
await HealthKitSync.startBackgroundSync({ serverUrl: window.location.origin, apiKey: key });
```

**Severity:** CRITICAL

**Description:** `NEXT_PUBLIC_*` values are inlined by Next at **build time** into the
client JS chunks. Three things compound:

1. **The platform guard doesn't protect the secret.** `Capacitor.getPlatform() !== "ios"`
   is a *runtime* check on line 33 — by the time it runs, the chunk containing the
   literal key string has already been downloaded by every web and PWA visitor. The
   no-op comment ("On web / PWA it is a complete no-op, so the deployed site is
   unaffected") is true of the *behaviour* and false of the *secret*.
2. **The chunks are not behind the passcode.** `middleware.ts:15` exempts `/_next`, line
   18 exempts anything ending in `.js`, and the matcher on line 47 excludes
   `_next/static` outright. So the bundle carrying the key is served with no Basic Auth
   at all. The setup doc's stated justification — "exposing it as `NEXT_PUBLIC_` inside
   the passcode-gated app is acceptable" — rests on a gate that does not cover the
   asset the key lives in.
3. **The endpoint it unlocks is also exempt.** `middleware.ts:16` exempts
   `/api/healthkit-sync` by design (external key-authed POSTs can't answer a Basic Auth
   prompt). The bearer check at `route.ts:573-574` is therefore the *only* thing
   standing between the open internet and the ingestion path.

Net: the sole credential for an unauthenticated, internet-reachable write endpoint
becomes a static string distributed to every client, unrotatable without a rebuild and
redeploy, and permanently retained by anyone who ever loaded the app once. The write
surface it grants is not read-only mischief — `processMetrics` **upserts** `weightLog`
(168-179), **updateMany**s `dailyActivity` steps and calories (127-160), upserts
`dailyRunningMetrics` and `dailyVO2Max`, and `processCycleTracking` writes
`cyclePhaseLog` for any day whose existing row isn't `source: "manual"` (554-561).
Cycle phase and HRV/RHR feed the daily Call directly. For a product whose entire thesis
is *"your baseline, learned from your own body data"*, silently poisoning that baseline
is the worst available outcome — worse than a read leak.

**Mitigating (and why it's still CRITICAL):** the web-side wiring is **uncommitted and
untracked**, so no deployed build contains the key today. That is exactly why this is
filed CRITICAL under the bugs.md convention ("must fix before next feature build") — it
is cheap to fix now and expensive after the first `git push` + `vercel deploy`, because
a leaked build artifact can't be recalled. Do not commit `native-health-init.tsx` in its
current form.

**Suggested fix:** don't put the ingestion key in the web bundle at all. In order of
preference:

1. **Provision the key natively.** The Swift already persists `bl_key` in
   `UserDefaults` and reads it there for every background POST — JS only needs to hand
   it over *once*. Move the literal into the iOS build (Info.plist entry or an
   xcconfig-injected build setting read by `startBackgroundSync`) and drop the
   `apiKey` argument from the JS call entirely. Zero web exposure, and the native
   binary is a far better place for it than a public CDN asset.
2. **Mint it server-side, gated.** Add a `GET /api/healthkit-sync/key` that is *not*
   middleware-exempt, returns the key only to a passcode-authenticated session, and
   have `native-health-init.tsx` fetch it on iOS before calling `startBackgroundSync`.
   The key then never enters a static chunk and rotation is a server env change.
3. Whichever path: rotate `HEALTHKIT_SYNC_KEY` when real auth lands (roadmap §5 step 2)
   and replace it with a per-user token, as the doc already plans. Note that step 3
   (TestFlight to training partners) currently *precedes* nothing that would fix this —
   a shared static write key does not survive contact with a second user.

### BUG-H1 — Body-mass unit mismatch: server converts lbs→kg, native module sends kg
**Files:** `src/app/api/healthkit-sync/route.ts:162-179`, `docs/capacitor-healthkit-setup.md` (quantityTypes table)

```ts
// route.ts:168
const weightKg = d.qty! * 0.453592;   // assumes HAE sent POUNDS
```
```swift
// capacitor-healthkit-setup.md
(.bodyMass, "weight_body_mass", .gramUnit(with: .kilo)),   // sends KILOGRAMS
```

**Severity:** HIGH

**Description:** The server's `weight_body_mass` case hardcodes a pounds→kilograms
conversion — correct for the Health Auto Export payloads it was written against. The new
Swift module reads `.bodyMass` in `.gramUnit(with: .kilo)` and posts the kilogram value
under the same metric name. The server will multiply it by 0.453592 anyway. A real 60 kg
weight lands in the database as **27.2 kg**, via an `upsert` on `userId_day` that
overwrites the correct value for that day. Nothing catches it: `MetricEntry.units` is
declared on line 14 but **never read anywhere in `processMetrics`**, and the 20–500 kg
validation from BUG-012 lives in `/api/weight`, not on this path — 27.2 passes any range
check that did exist. Downstream, `tdee.ts` consumes `weightLog` and will produce a
nonsense energy balance from a fabricated 55% weight drop.

**Suggested fix:** stop inferring units from the producer. Read `metric.units` in
`processMetrics` and convert explicitly (`lb`/`lbs` → ×0.453592, `kg` → ×1, unknown →
reject the metric and record it in the `HealthKitSync.details` string rather than
guessing). Simultaneously change the Swift to `.pound()` if you'd rather not touch the
server before the cutover — but the unit-aware server is the durable fix, since the same
class of mismatch is live for `walking_running_distance` (Swift sends km; the HAE-era
rows in `dailyRunningMetrics.walkingRunningDistance` were whatever HAE's export setting
produced, and the column has no unit) and will recur for every future producer.

### BUG-H2 — Body-fat percentage: HealthKit `.percent()` is a 0–1 fraction, stored as if 0–100
**Files:** `src/app/api/healthkit-sync/route.ts:181-197`, `docs/capacitor-healthkit-setup.md` (quantityTypes table)

```swift
(.bodyFatPercentage, "body_fat_percentage", .percent()),
```
```ts
update: { bodyFatPct: d.qty },   // route.ts:189 — stored raw
```

**Severity:** HIGH

**Description:** `HKUnit.percent()` yields a **fraction**, where `1.0` means 100%. A 22%
body-fat sample arrives as `0.22` and is written straight into `WeightLog.bodyFatPct`,
which every other writer treats as 0–100 (BUG-012 validates 1–80 on `/api/weight`). Same
silent-corruption shape as BUG-H1, same `upsert` that overwrites a correct prior value.
Worse in one respect: `0.22` is truthy, so the `.filter((d) => d.qty && d.date)` guard on
line 182 passes it through unchallenged. And line 190's `create` branch is more damaging
than the `update` branch — it writes the raw fraction *and* seeds `weightKg: 0`, so a
body-fat sample for a day with no existing `WeightLog` row creates a phantom zero-weight
entry that `tdee.ts` will then consume.

**Related, and repo-wide on this path:** that `d.qty &&` truthiness filter silently drops
legitimate **zero** readings, and it's used at lines 104, 129, 146, 163 and 182 (and in
`Avg ?? qty` form at line 81) — not just here. A true 0-step or 0-active-calorie day is
discarded rather than recorded, which is a meaningful distinction for a system that's
supposed to learn a baseline including rest days. Prefer `d.qty != null` at all six sites.

**Suggested fix:** multiply by 100 at the unit-conversion layer added for BUG-H1, and
add a range assertion (1–80) on this path mirroring the `/api/weight` validation so a
future unit change fails loudly instead of writing a plausible-looking wrong number.
Drop the `weightKg: 0` seed from the `create` branch — a body-fat reading is not evidence
of a zero body weight; either look up the day's weight or leave the row uncreated.

### BUG-H3 — First-launch backfill is unbounded and fails into a permanent retry deadlock
**File:** `docs/capacitor-healthkit-setup.md` (`collectAndPost`, `newSamples`)

```swift
let q = HKAnchoredObjectQuery(type: type, predicate: nil, anchor: anchor,
                              limit: HKObjectQueryNoLimit) { ... }
...
guard (resp as? HTTPURLResponse)?.statusCode == 200 else { throw ... }
commitAnchors() // only advance anchors after a successful POST
```

**Severity:** HIGH

**Description:** On first launch every anchor is `nil`, so `HKAnchoredObjectQuery` with
`HKObjectQueryNoLimit` and `predicate: nil` returns the user's **entire HealthKit
history** for all 15 quantity types plus workouts plus menstrual flow. For an Apple Watch
worn for a couple of years, `heartRate` alone is comfortably 10⁵–10⁶ samples. The module
materializes all of it into one `[[String: Any]]` envelope and POSTs it as a single body.

Vercel caps serverless request bodies at ~4.5 MB and rejects oversize requests at the
platform edge — the handler never runs, so none of `route.ts`'s careful error logging
fires and no `HealthKitSync` row is written. The Swift then throws on the non-200, which
means `commitAnchors()` on the next line **is never reached**. The anchors stay `nil`.
Every subsequent observer firing rebuilds the identical oversize payload and fails
identically, forever. This is the same failure signature as the 16-day silent HAE outage
the 2026-05-27 observability fix was written for — except this one is invisible to that
fix, because it fails upstream of the handler.

The `maxDuration = 300` on line 8 ("allow up to 5 minutes for large backfills") is
addressing timeout, not body size, and so provides no cover here.

**Suggested fix:** two changes, both needed.
1. **Chunk the upload.** Cap each POST (e.g. 5,000 samples or ~1 MB serialized), send
   sequentially, and commit each type's anchor after *its* batch succeeds — currently
   `commitAnchors()` is all-or-nothing across every type, so one bad type also blocks
   the anchors of the 15 healthy ones.
2. **Bound the first sync.** Add an `HKQuery.predicateForSamples(withStart:)` floor on
   the anchor-less path (90 days is more than enough to seed a personal baseline; the
   learning period in the personalization model is ~1 month). Full history is not worth
   a deadlock.
3. Additionally, treat a 413/4xx differently from a 5xx — a non-retryable status should
   surface to the user rather than silently re-queue.

### BUG-H4 — Concurrent `collectAndPost()` calls race on shared `pendingAnchors`, losing samples
**File:** `docs/capacitor-healthkit-setup.md` (`registerObserver`, `pendingAnchors`, `commitAnchors`)

```swift
private var pendingAnchors: [String: HKQueryAnchor] = [:]   // plain dict, no isolation
...
let query = HKObserverQuery(sampleType: type, predicate: nil) { [weak self] _, completion, _ in
    Task { _ = try? await self?.collectAndPost(); completion() }
}
```

**Severity:** HIGH

**Description:** `startBackgroundSync` registers **up to 17 observers** (15 entries in the
`quantityTypes` array + workouts + menstrual flow; the `guard let type = ... else { continue }`
means an identifier unavailable on the running OS version is silently skipped rather than
reported — worth logging, since a dropped type looks identical to "no data for that type").
Each observer's callback runs the *full* `collectAndPost()`
sweep across all types. A single Watch sync writes many types at once, so multiple
observers fire near-simultaneously and spawn concurrent, unserialized `Task`s. All of them
mutate the same non-isolated `pendingAnchors` dictionary and then call
`commitAnchors()`, which writes **and clears** it.

Two concrete consequences:
- **Data race.** Concurrent writes to a Swift `Dictionary` from multiple tasks is
  undefined behaviour, not merely a lost update. Under Swift 6 strict concurrency this
  won't compile; under Swift 5 it will crash intermittently.
- **Silent sample loss.** Task A reads new samples and stashes anchors; Task B's POST
  succeeds first and calls `commitAnchors()`, persisting *A's* anchors along with its
  own. If A's POST then fails, A's samples are gone — the anchor has already advanced
  past them and `HKAnchoredObjectQuery` will never return them again. This loses data
  permanently and invisibly, which for a longitudinal-baseline product is the most
  costly failure mode in this document after BUG-C1.

There is also plain **amplification**: N observers × full-sweep-over-N-types means one
Watch write can trigger 17 full sweeps and 17 POSTs of overlapping data.

**Suggested fix:** make the plugin an `actor` (or serialize through a dedicated
`DispatchQueue` / `AsyncChannel`) so only one `collectAndPost()` runs at a time, and
coalesce observer firings with a short debounce (~30–60s) so a burst of type-writes
produces one sweep. Scope anchor commits per type as noted in BUG-H3. Keep calling
`completion()` unconditionally in the observer — the current code does this correctly and
it must stay that way or iOS throttles delivery.

## Medium

### BUG-M1 — `/api/healthkit-sync` has no rate limit or body cap, and its producer just changed from daily-batch to per-write
**File:** `src/app/api/healthkit-sync/route.ts:8, 569-606`

**Severity:** MEDIUM

**Description:** BUG-004 pattern, non-Anthropic variant. The endpoint has `maxDuration = 300`,
no request-size validation, no rate limiting, and no per-caller accounting. That was
tolerable when the only client was Health Auto Export posting once a day. The native
module changes the traffic shape fundamentally: `enableBackgroundDelivery(frequency: .hourly)`
across 17 types, each firing a full sweep (see BUG-H4). Combined with BUG-C1 — a
gate-exempt endpoint whose key is public — an unbounded 300-second-budget handler that
opens a `$transaction` per 500-row batch is a straightforward way to exhaust the free-tier
Supabase connection pool, which per `roadmap-2026-08.md` §3 already took prod down on
Aug 15–16 for unrelated reasons.

**Suggested fix:** reuse the in-memory limiter pattern from the BUG-004 coach fix (e.g.
30 req/hour per key), reject bodies over a fixed size before parsing, and cap
`data.metrics[].data.length` per request with a 413 that names the limit so the client can
chunk (pairs with BUG-H3's chunking).

### BUG-M2 — `requestAuthorization`'s `granted` flag doesn't mean the user granted anything
**Files:** `src/components/native/native-health-init.tsx:43-44`, `docs/capacitor-healthkit-setup.md` (`requestAuthorization`)

```swift
store.requestAuthorization(toShare: nil, read: allReadTypes()) { ok, err in
    if let err = err { call.reject(...) } else { call.resolve(["granted": ok]) }
}
```
```ts
const { granted } = await HealthKitSync.requestAuthorization();
if (cancelled || !granted) return;
```

**Severity:** MEDIUM

**Description:** HealthKit deliberately does **not** disclose read-authorization status —
revealing that a user declined to share, say, cycle data would itself leak health
information. The `success` flag in the completion handler means only "the permission sheet
was presented without error." It is `true` when the user taps *Don't Allow* on everything.
So the `!granted` early-return on line 44 never fires, and the app has no way to
distinguish "authorized, no data yet" from "denied." Compounding it, the only failure
signal anywhere in the bootstrap is `console.warn` on line 56 — invisible on a phone. The
user gets an app that silently shows no Watch data, with no explanation and no retry
affordance, and iOS will not re-prompt after a denial (it requires a manual trip to
Settings → Health → Data Access & Devices). Given roadmap §5 step 1 makes "Allow Health
access" the *entire* onboarding, a silently-denied permission is an unrecoverable
first-run.

**Suggested fix:** stop treating `granted` as truth. Detect authorization empirically —
after `syncNow()`, if `posted === 0` and there is no prior successful `HealthKitSync` row,
render an in-app banner explaining how to grant access in Settings, with a "retry" that
re-runs `syncNow()`. Optionally use `store.authorizationStatus(for:)` for *share* types as
a weak proxy, but don't rely on it for read types. Either way, surface the state in the UI
rather than `console.warn`.

### BUG-M3 — `DateFormatter` without a fixed locale emits non-Gregorian dates on some devices
**File:** `docs/capacitor-healthkit-setup.md` (`collectAndPost`)

```swift
let df = DateFormatter()
df.dateFormat = "yyyy-MM-dd HH:mm:ss Z"
```

**Severity:** MEDIUM

**Description:** A `DateFormatter` with a hardcoded `dateFormat` but no
`locale = Locale(identifier: "en_US_POSIX")` respects the device's regional calendar. On a
phone set to the Japanese, Buddhist, or Republic-of-China calendar, `yyyy` renders the era
year — e.g. `2569-08-17` under the Buddhist calendar. The server takes
`d.date.substring(0, 10)` and hands it to `dateStrToUTC` (`date-utils.ts:14`), which does
`new Date(dateStr + "T00:00:00.000Z")` with no validation, producing a date ~543 years in
the future that is then used as the `userId_day` upsert key. Rows land in days that no
query will ever surface, and `new Date(d.date)` for the heart-rate timestamps yields
`Invalid Date`, which Prisma rejects — failing the whole 500-row `$transaction` batch. Not
a risk for a single US-locale device today; it becomes one at roadmap §5 step 3
(TestFlight to other people). This is also the standard Swift date-formatting footgun,
so it's worth fixing reflexively rather than after a bug report.

**Suggested fix:** set `df.locale = Locale(identifier: "en_US_POSIX")` and
`df.calendar = Calendar(identifier: .gregorian)` — one line each, no downside. Separately,
add a `/^\d{4}-\d{2}-\d{2}$/` guard in `dateStrToUTC` or at the ingestion boundary so a
malformed date is rejected with a recorded reason instead of silently becoming a garbage
`Date`.

### BUG-M4 — Native workout payload coerces missing distance/energy to `0`, and may duplicate HAE-era workouts
**Files:** `docs/capacitor-healthkit-setup.md` (workouts block), `src/app/api/healthkit-sync/route.ts:437-469`

```swift
"activeEnergyBurned": ["qty": w.statistics(...)?.sumQuantity()?.doubleValue(for: .kilocalorie()) ?? 0, "units": "kcal"],
"distance": ["qty": (w.totalDistance?.doubleValue(for: .meterUnit(with: .kilo)) ?? 0), "units": "km"],
```

**Severity:** MEDIUM

**Description:** Two problems in the same block.

*(a) The distance/calorie fields have no null-preservation at all — the HR fix was never
extended to them.* `route.ts:446-450` guards the HR writes behind `if (avgHR != null)`,
per the comment on lines 433-436 ("prevents a re-export that lacks HR samples from wiping
a previously-populated HR series"). Lines 442-443 have **no such guard**:
`activeCalories: w.activeEnergyBurned?.qty ?? null` and `distance: w.distance?.qty ?? null`
are written unconditionally into `updateData`, and `?? null` writes an *explicit* `null` —
Prisma nulls the column. So a producer that omits the field already wipes stored data on
every re-sync, today, independent of anything the native module does. The Swift's `?? 0`
changes the failure from "wiped to null" to "wiped to zero" — arguably the less
destructive of the two, and a `0` distance on a strength workout is at least not *wrong*.
The real finding is the asymmetry itself: the 2026-05 HR fix hardened one of three fields
and the other two were left to overwrite on every upsert. The cutover matters only because
it's about to drive this path much harder.

*(b) Workout identity across the HAE→native cutover is unverified.* The upsert keys on
`userId_externalId` (line 453) and the Swift supplies `w.uuid.uuidString`. **Unverified —
worth checking before the cutover:** whether HAE's `id` field is also the HealthKit sample
UUID. If it is, workouts re-sync cleanly and only problem (a) applies. If it isn't, every
historical workout gets a second row under a new id, double-counting volume, calories, and
session counts in every trend that aggregates `healthKitWorkout`. Confirm by diffing one
known workout's stored `externalId` against its HK UUID before uninstalling HAE.

**Suggested fix:** (a) mirror the HR conditional on the server — build `updateData`
incrementally and only assign `distance`/`activeCalories` when the incoming value is
non-null, so an omitted field leaves the column alone. This is the load-bearing half and
it fixes the existing bug, not just the incoming one. Separately, have the Swift emit
`nil` rather than `0` for absent statistics (`if let` the optionals, only add the keys
when present) so the server can tell "no distance" from "zero distance". (b) Run the
`externalId` comparison above; if the schemes differ, write a one-time migration mapping
HAE ids to HK UUIDs before the cutover, and keep HAE installed until it's verified.

### BUG-L2 — `serverUrl` derived from `window.location.origin` and then persisted indefinitely
**Files:** `src/components/native/native-health-init.tsx:47`, `docs/capacitor-healthkit-setup.md` (`startBackgroundSync`)

**Severity:** LOW

**Description:** `startBackgroundSync` writes `serverUrl` into `UserDefaults` under
`bl_server`, and `collectAndPost` reads it for every subsequent background POST. If
Capacitor ever falls back to the bundled `webDir` — first launch offline, or `server.url`
unreachable — `window.location.origin` is `capacitor://localhost`, and that gets persisted
as the sync target. Background posts then fail silently, swallowed by the `try?` in
`registerObserver`. It self-heals on the next successful foreground launch (the effect
re-runs and overwrites `bl_server`), which is why this is LOW rather than higher.

**Suggested fix:** validate the origin before persisting — refuse to store anything that
isn't `https:` — and have the Swift skip the POST (rather than fail) when `bl_server`
doesn't parse as an https URL.

### BUG-L3 — `cancelled` flag doesn't cancel the operations that matter
**File:** `src/components/native/native-health-init.tsx:27,44,60-62`

**Severity:** LOW

**Description:** The cleanup sets `cancelled = true`, but it's only checked once — on line
44, between `requestAuthorization` and `startBackgroundSync`. If the component unmounts
during `startBackgroundSync` or `syncNow`, both still run to completion and
`startBackgroundSync` still registers 17 permanent observers. Harmless in practice, since
`layout.tsx` mounts this at the root and it never unmounts in a normal session, and the
native side is idempotent. Noted for correctness only.

**Suggested fix:** check `cancelled` before each awaited step, or drop the flag and the
cleanup entirely rather than implying a cancellation guarantee the code doesn't provide.

## Notes

- **The feature's web half is uncommitted.** `src/components/native/native-health-init.tsx`
  is untracked and the `layout.tsx` mount is unstaged, so `3f334db` as committed does *not*
  wire anything up — the deployed Vercel build is unchanged and contains no
  `NEXT_PUBLIC_HEALTHKIT_SYNC_KEY`. This is the whole reason BUG-C1 is still cheap: fix the
  key provisioning *before* this is committed and pushed, because a build artifact
  containing the key can't be un-published.
- **Severity skew is real, not alarmism.** Four of the five Critical/High findings are
  silent data-corruption or silent data-loss bugs (H1, H2, H3, H4), and they share a root
  cause: `/api/healthkit-sync` was written against one specific producer's conventions
  (HAE's units, HAE's cadence, HAE's id scheme) and those conventions are now being
  swapped out without a contract between the two halves. The single highest-leverage fix
  is not any individual bug — it's **making the endpoint validate what it receives**
  (read `metric.units`, range-check values, reject malformed dates, cap payload size)
